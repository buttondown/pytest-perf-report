What to do about it

  1. high 1 flaky test needed reruns to pass
    Reruns hide real race conditions and tax every run: tests/test_b.py::test_flaky (2×). Make them deterministic (frozen time, seeded randomness, event-driven waits) rather than retrying.
  2. high Fix the 1 failing test
    Nothing below matters until the suite is green: tests/test_a.py::test_p[two].
  3. high Tests are talking to the real network
    2 socket connection(s) left the machine (93.184.216.34:443). Real network calls make tests slow, flaky, and dependent on third-party uptime. Mock them (responses/respx/vcrpy) and enforce hermeticity with pytest-socket.
  4. medium Probable N+1 queries: 1 query shape(s) repeat ≥25× inside a single test
    Worst: SELECT on u runs up to 40× in one test (in tests/test_a.py::test_p[one]) — 120 times suite-wide. Batch it (select_related/prefetch_related, joins, or bulk fetches) — that usually speeds up production too.
  5. low 1 tests (17%) are skipped
    Skips silently stop protecting you. Re-enable what can run, delete what can't, and put a reason + owner on the rest.
  6. low 1 test(s) raised peak memory by >100MB
    Worst: tests/test_b.py::TestX::test_slow (+150.0MB). Peak RSS never comes back down, so one hungry test sets the memory floor for the whole worker — stream instead of materializing, or shrink the fixture data.
  7. low 400 file opens (~67 per test)
    Re-reading the same file is cheap to cache at module or session scope. Start with fixtures/big.json: 12 opens × 2.0MB ≈ 24.0MB re-read.
